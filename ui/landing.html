01

Memory isn't one thing. This agent keeps three.

Each is read at a different moment, written by different code, and lives for a different length of time. Collapsing them into one vector store is what makes agents feel amnesiac despite "having RAG".

Semantic

What I believe

Your standing terms, and the clause patterns that have harmed you before. Searched once per clause, over a distributed vector index.

AsyncCockroachDBVectorStore → guardian_memory
Episodic

What happened with this client

One durable thread per client. Reopening it months later replays the whole negotiation, so nothing you already conceded gets re-demanded.

CockroachDBChatMessageHistory → guardian_chat_history
Procedural

Where the work got to

Workflow state written after every step. Kill it mid-review and the next run picks up from the last completed node.

AsyncCockroachDBSaver → checkpoints

03

The dangerous contract is the one that looks fine.

Pattern matching finds bad clauses that are present. It cannot see a protection that was simply never written — which is exactly how a polished, well-drafted template still leaves you exposed. So the whole rule set is checked against the document, and what nobody wrote down gets raised too.

Fig. 2 — vector search returns rules that resemble what the contract says, so a missing protection can never surface that way.

The finding

One clause failing you across five clients isn't a client problem.

It's a missing term in your own contract. No single review can reach that conclusion — it exists only because every decision was written somewhere queryable.

SELECT f->>'clause'                AS clause,
       count(*)                    AS times_flagged,
       count(DISTINCT client_name) AS clients
FROM   agent_audit_log,
       jsonb_array_elements(decision->'findings') AS f
GROUP  BY 1
ORDER  BY times_flagged DESC;
